# Keddeh Cross-Sector Recursive Application Skill

## Purpose
Use the existing Keddeh estate as a graph of authoritative sectors. Carry one work envelope across those sectors without duplicating implementations, flattening ownership, losing failures, or confusing a missing canonical repository with a missing executable mechanic.

## Mandatory decision test
Before every consequential transition ask: **AM I DOING WHAT I SHOULD BE DOING?**

Resolve the answer against the actual work intent, current state, owning sector, available mechanic and required readback.

## Operating rule
1. Verify the current work envelope and identity root.
2. Resolve legal identity through `KEDDEH_LEGAL_IDENTITY_ADAPTER_R1.py`.
3. Resolve the owning sector through `KEDDEH_CROSS_SECTOR_RECURSIVE_ADAPTER_R1.py`.
4. Prefer the canonical repo when it exists.
5. If the canonical repo does not yet exist, use only the explicitly declared transitional implementation repo; never infer ownership from file location.
6. Hand off references and required state, not whole copied systems.
7. The handoff does not count as target execution.
8. Invoke the existing target mechanic.
9. Require its mutation receipt and readback.
10. Append evidence and failure state to the same work envelope.
11. Increment the continuation epoch and recurse from the actual result.

## Shared work envelope
`work_id + organisation_identity + operating_identity + intent + state + lineage + evidence + continuation + envelope_root`

## Identity invariant
- legal entity: `organisation://the-layna-company`
- operating identity: `business-name://keddeh-systems`

Downstream sectors may consume these identities but may not redefine their relationship.

## Mutation rule
Only the target sector owns its mutation. BRAINK may orchestrate and route, but orchestration is not ownership.

## Evidence rule
A representation, manifest, handoff, plan or registry entry is never promoted to execution evidence. Promotion requires the target sector's actual receipt/readback.

## Recursion rule
`ADDRESS -> RESOLVE -> AUTHORIZE -> APPLY -> RECEIPT -> OBSERVE -> REWRITE -> NEXT ADDRESS`

Continue until the real mechanical boundary, not until the current carrier becomes inconvenient.
